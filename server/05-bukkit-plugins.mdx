Most of the Minecraft server ecosystem is Bukkit, Spigot and Paper plugins that will never be rewritten.
Basalt runs them next to Lua plugins, without a Java installation on the host.

## Drop it in

Put the `.jar` in `plugins/` and start the server. Lua packages live in the same folder.

```
plugins/
  my-lua-plugin/        Lua plugin (a folder with plugin.toml)
  other.bspkg           Lua plugin (a package)
  WorldEdit.jar         Bukkit plugin (a jar with plugin.yml or paper-plugin.yml)
```

What is inside the file decides its kind, not its name. `/plugins` lists both kinds. A jar without a `plugin.yml`
is reported once and ignored. Restart the server to pick up a jar added later.

<x-docs.callout type="note" title="Nothing starts until you need it">
With no Bukkit jar in `plugins/`, no Java machine starts and nothing Java is read. With one, the server starts
Basalt Shim, its embedded Java machine, and loads the jar.
</x-docs.callout>

The libraries a plugin expects from the server (Paper API, Adventure, Guava, Gson, Netty and others) come with it.
If a copy of the server lacks them, they are downloaded once into `.basalt/bukkit/lib/` and each is checked against
its published SHA-1.

## How it maps to the native API

A Bukkit call is not a second server inside Basalt. Each one is translated into the same services the Lua API uses,
so a Lua plugin and a Bukkit plugin see one world.

| Bukkit | Native service |
|---|---|
| Events and `Listener` priorities | The Basalt event bus (`on` and `watch`) |
| `World`, `Block`, `BlockData`, `Chunk` | The [world API](/docs/server/world-api): sections, block entities, biomes |
| `Entity`, `Player`, `Inventory` | The entity and player objects |
| Plugin messaging channels | `channel.on` and `channel.send` |
| Netty pipelines (PacketEvents) | The [packet API](/docs/server/packets) |
| Commands from `plugin.yml` | Server commands; a command with no permission is open to everyone |

Block edits made through the usual calls (`setType`, `setBlockData`, `BlockState.update`) are grouped per chunk
section and sent to the world when the plugin's callback, be it an event, a command or a task, returns. Reads inside
the callback see the pending writes.

## Worked with

WorldEdit and FastAsyncWorldEdit load and run through the adapter for this Minecraft version that they carry
themselves: selections, `//set`, `//replace`, `//copy`, `//paste` and `//undo` change the blocks players see and the
blocks the server reads back. PacketEvents loads and sees every packet of every connection state. The server offers
the Minecraft classes those adapters expect (chunks, palettes, block states, registries), so nothing is looked up by
plugin name.

## Not supported yet

- Plugins that reach into Minecraft's internals (reflection on NMS classes) beyond what the packet and WorldEdit
  support above provides.
- Bedrock players do not exist for packet listeners, because they have no Java packets.
- `ItemMeta` is limited to the item type and the amount, and regenerating chunks, growing trees and placing structures
  from a plugin are missing.
- Chests with their items, signs with their text, entities and biomes in a WorldEdit copy, paste or schematic, and the
  light of the blocks it places.
- Removing an entity by UUID from a WorldEdit operation.

## Setup

None. The Java machine and the Bukkit layer are inside the server binary. The first time a Bukkit jar is in `plugins/`,
the server unpacks them into `.basalt/bukkit/` and downloads the few libraries they need once, each checked against its
published SHA-1. After that it starts offline.

## When to use which

| You want | Use |
|---|---|
| Maximum performance, native execution | Native Lua plugins |
| Existing plugins | Bukkit and Paper jars |
| Both | Both, side by side |

Native plugins are the fast path: no process boundary, no serialization and no second heap. Bukkit support exists so
that adopting Basalt does not mean giving up the plugins your server relies on while you migrate.
