A proxy session has a client protocol and a backend protocol. Supporting both separately does not imply that every pair is supported. The native Java protocol is currently Minecraft 26.3 (777).

## Java versions

| Client | Backend | Behaviour |
|---|---|---|
| Current native | Current native | Relay on the native protocol. |
| Supported older client | Current native | Translate here, or delegate to a capable Basalt Server. |
| Current native | Supported older backend | Translate the backend protocol upward for the client. |
| Older protocol N | Same protocol N | Same-version relay for the listed supported backends. |
| Older protocol N | Different older protocol M | No general arbitrary older-to-older bridge; select another compatible destination. |

Same-version relay is supported for the older protocols listed in this table. Set a backend's `protocol` in `servers.toml` to its actual protocol, or use `"client"` only for a server that accepts each client's version. `"auto"` means follows-client for Basalt forwarding and current-native for other schemes, not server-version discovery.

When the initial route contains incompatible servers, they are skipped. A client with no supported route sees the unsupported-version or no-compatible-server message. A requested move to an incompatible backend leaves the player on the current server.

### Who translates

Choose `[translation] mode` in `proxy.toml`:

| Mode | Policy |
|---|---|
| `auto` | Delegate to a capable Basalt backend; otherwise translate supported routes on the proxy. |
| `server` | Delegate or relay a compatible same-version session, without proxy-side translation. |
| `proxy` | Translate here, including toward Basalt backends. |
| `off` | Require matching client/backend protocols and do not offer the session envelope. |

For delegation, configure the backend with `forwarding = "basalt"` and `protocol = "auto"` or `"client"`. On Basalt Server enable `[network.forwarding] session-envelope = true` with matching keys and backend identity. The envelope carries the original client session to the backend for translation, including clients too old for ordinary login queries.

### Switching and content

Java clients from 1.20.2 reconfigure in place when moving between backends. Older clients receive a new join sequence and have additional restrictions when mixing translated and raw relay paths. Test the actual source and destination combination, not just a first join to each one independently.

Registries come from the destination backend and are refreshed during a supported switch. The proxy does not invent unavailable content or provide universal mod compatibility. Version-dependent packets, item components and client UI can have translation limits even when a login route exists.

### Modded backends

A compatible Java backend can sit behind the proxy, but its forwarding support must match. Modern forwarding on Fabric or another modded server requires a suitable forwarding mod. Modpack login channels and client requirements remain the modpack's responsibility; forwarding ordinary configuration/play traffic is not a guarantee that every modpack works.

## Bedrock Edition

Enable the Bedrock listener separately in `proxy.toml`:

```toml
[bedrock]
enabled = true
transport = "both"
port = 19132
nethernet-port = 0
advertise-address = ""
```

The bridge advertises game version `1.26.60` and recognises Bedrock protocols `1001`, `2168`, `2169`, `2193` and `2225`. Newer clients using NetherNet cannot join a RakNet-only listener. The proxy's `--version` reports its native Java version, not this Bedrock transport configuration.

### Ports and transports

| Mode | Required listeners with defaults |
|---|---|
| `both` | RakNet UDP 19132, NetherNet TCP signaling 19132 and NetherNet game UDP 19133. |
| `nethernet` | TCP signaling 19132 and game UDP 19132. |
| `raknet` | UDP 19132 only, for clients using RakNet. |

`nethernet-port = 0` selects the Bedrock port when RakNet is off, otherwise the following port. An explicit value chooses the game UDP port. Forward every enabled transport through the firewall/container/NAT, and set `advertise-address` to the reachable public game address behind NAT.

When both transports are requested, one may remain available if the other fails to bind; check startup warnings rather than assuming a running proxy has both. The NetherNet identity is persisted in `.basalt/nethernet-identity.der`.

Bedrock server-list text is drawn from the proxy's server-list service, not a `[bedrock] motd` setting. See [Interface](/docs/proxy/interface).

### Routing and delegation

A Bedrock player enters the first backend of `[routing] try`; forced hosts do not select a Bedrock game mode. In proxy-translation mode the proxy opens a Java connection and translates between editions. The bridge supports backend changes, but do not assume Java's full route recovery behaviour applies to Bedrock.

With `[bedrock] delegate = true`, a Basalt-forwarding backend can serve the Bedrock session through the session envelope instead. Configure Basalt forwarding and envelope support on that server. Delegating does not make a Paper backend understand Bedrock.

### Authentication and identity

With proxy online mode enabled, require an Xbox Live-signed Bedrock identity. Offline mode permits unsigned identities and is inappropriate for a public network relying on names for access. The antibot can also require Xbox authentication during attacks.

When bridged to Java, the name is `_` followed by the sanitised gamertag, using letters, digits and `_`, limited to 16 bytes. The UUID is the offline UUID of that resulting name, not a Mojang premium UUID. Sanitisation and truncation can produce collisions between gamertags; the prefix is a naming convention, not proof of a Java account.

Basalt forwarding carries edition and XUID metadata. Other schemes lack those fields. A vanilla backend with `none` loses forwarded premium identity, just as it does for Java players. There is no built-in Java/Bedrock account-linking service.

### Gameplay and messages

The bridge handles chunks, movement, chat and commands, entities, health, inventory/equipment interactions and client HUD packets for its supported paths. It also handles a subset of container screens. Do not treat protocol acceptance as complete equivalence of every screen, entity appearance or client interaction.

Backend resource packs and client-specific content are not converted into Bedrock packs by the proxy. Test required resource-pack policies before moving a Bedrock player onto that backend. Do the same for crafting, specialised containers and modded gameplay. Delegated sessions use the Basalt Server path and its capabilities.

To resolve backend translation keys such as join/death messages, set `[bedrock] language` to a local official server jar or `en_us.json`. No language data is downloaded, and an empty setting leaves raw keys.

### Bedrock protection

`antibot.toml` has a separate `[bedrock]` table for packet rate, login time, connection scoring and attack-time limits. It shares reputation, bans and attack mode with Java by origin. See [Antibot](/docs/proxy/antibot#bedrock).

## Test a mixed network

Validate a Java first join, a Java move in both directions, a backend failure and each Bedrock transport you expose. Include an incompatible client to check that it receives the intended message. Keep authentication enabled when validating production identity; an offline smoke test only establishes transport behaviour.
