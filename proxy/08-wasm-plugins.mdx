A proxy plugin is a small WebAssembly program that runs inside Basalt Proxy. It can greet players as they join, add
commands, send a player to another backend, turn a login away, rewrite the entry in the server list, filter chat, show
boss bars and talk to your backends. You write it in any language [Kiln](/docs/server/wasm-kiln) supports (C, C++, Zig,
Rust, AssemblyScript, Go, Kotlin, C# and Java), compile it to a `.wasm` module and drop it in the proxy's `plugins`
folder.

A plugin runs in a sandbox. It cannot open files or sockets by itself, it only does what the proxy API offers, and one
that crashes or hangs is switched off without taking the proxy down. If you have written a plugin for Basalt Server the
tools are the same: the same Kiln, the same SDK, the same manifest. What changes is the set of things you can do, see
[How a proxy plugin differs from a server plugin](#how-a-proxy-plugin-differs-from-a-server-plugin).

The examples use the C++ SDK, where a call is written `area::function` (for example `players::send` or `events::on`).
The other languages use the same names with their own casing, see [The SDK](/docs/server/wasm-sdk).

## Quickstart

Install Kiln (see [Kiln](/docs/server/wasm-kiln)), then create, build and pack a plugin for the proxy:

```bash
kiln new greeter --lang cpp --target proxy
kiln build greeter
kiln pack greeter
```

`kiln new` writes a ready-to-run plugin into `greeter/`: a manifest (`plugin.toml`), the code (`src/main.cpp`), a
configuration file and a language file under `resources/`. The first build downloads the compiler for the language if
it is not installed yet. `kiln pack` writes `greeter/build/greeter-0.1.0.bppkg`, a package ready for the proxy.

Copy the package into the `plugins` folder next to where you run the proxy and start it (or type `reload` in the
console of a running proxy):

```
[INFO] [Plugin greeter]: wrote plugins/greeter/config.toml
[INFO] [Plugin greeter]: wrote plugins/greeter/lang/en_us.toml
[INFO] [Plugin greeter]: starting up
[INFO] [Proxy]: Loaded 1 plugin(s).
```

Type `plugins` in the console to list what loaded (in game, `/plugins` needs the `basalt.command.plugins` permission):

```
Plugins (1): greeter
```

The starting point greets a player on join, counts their visits, adds a `greeter hello` command and announces itself on
a timer. Run `greeter hello` in the console and the reply appears in the log under the plugin's name.

## A first plugin

Replace `src/main.cpp` with a plugin that greets every player who joins and answers a command:

```cpp
#include <basalt/proxy.hpp>

using namespace basalt::proxy;

static void on_join(core::Ctx ctx) {
    const core::Player player = events::event_player(ctx);
    if (player == 0) {
        return;
    }
    core::Args args;
    args.add("name", players::player_name(player).c_str());
    players::send(player, "@welcome", &args);
}

static void hello(core::Ctx ctx) {
    const core::Player player = events::event_player(ctx);
    core::Args args;
    args.add("name", commands::command_source_name(ctx).c_str());
    args.add("server", player == 0 ? "the console" : players::player_server(player).c_str());
    commands::command_reply(ctx, "@hello", &args);
}

void plugin_init() {
    log::log_info("greeter is ready");
    events::on("player.join", core::kNormal, on_join);
    commands::command("greeter hello", "", hello);
}
```

The text lives in `resources/lang/en_us.toml`:

```toml
welcome = "<green>Welcome to the network, <yellow>{name}</yellow>!"
hello = "<gray>Hello, {name}. You are on <aqua>{server}</aqua>."
```

Build, pack, copy the package over the old one and run `reload`. A player who joins gets the welcome line, and
`/greeter hello` answers with their current backend.

What the code does:

- `plugin_init` is where the plugin starts. The proxy calls it once when the plugin loads, and everything you want to
  react to is registered there.
- `events::on` listens to an event by name and gives your function a `ctx`, the context of that one call. It is only
  valid while the function runs. `events::event_player(ctx)` turns it into a player handle, or 0 when the event is not
  about a connected player.
- Handlers are plain functions. They cannot capture variables, so keep what they need in the plugin's data, in the
  configuration or in `static` variables.
- A text that starts with `@` is a key of the language file, anything else is written directly in
  [MiniMessage](https://docs.advntr.dev/minimessage/) (`<green>Hello</green>`). `core::Args` fills the `{name}` fields.
  See [Text](/docs/server/wasm-text).
- `commands::command("greeter hello", "", hello)` registers the words `greeter hello`. The empty second argument means
  anyone may run it. The reply goes to the player as a chat line, and to the proxy log when the console ran it.

## Where plugins live

The proxy looks for plugins in the `plugins` folder of its working directory and creates it if it is missing. Each plugin
is one of:

- a `.bppkg` package, which is what `kiln pack` produces (a zip archive with `plugin.toml`, the module and the
  `resources` folder);
- a folder named after the plugin's `id`, with `plugin.toml` and the module inside, handy while testing. It reads its
  language files from a `lang` folder inside it and its configuration from `config.toml` or `resources/config.toml`.

Plugins load when the proxy starts and again on the `reload` console command. A reload stops every plugin, reads the
folder again and starts them, and keeps the data they saved. Plugin state kept in memory is lost, so save what matters
in the plugin's [data](/docs/proxy/wasm-events#commands-tasks-config-and-player-data).

The first time a package loads, everything under its `resources` folder is copied into `plugins/<id>/`, skipping files
that already exist. The server owner edits those copies, and updating the package never overwrites them. The module is
compiled once and cached under `.basalt/wasm-cache`; a module may be up to 16 MiB. Per-player data is kept in
`.basalt/players.db`.

A package that cannot load is skipped, and the log says why: a missing or invalid `plugin.toml`, an `abi` or `api` the
proxy does not speak, a missing dependency, a second plugin with the same `id`, or an error while the plugin starts.

### The `[plugins]` table

The operator controls the plugin host in `config/proxy.toml`:

| Key | Default | Meaning |
|---|---|---|
| `enabled` | `true` | Whether the `plugins` folder is looked at. `false` loads nothing. |
| `queue-size` | `256` | How many events can wait for the plugin thread (1 to 65536). A full queue drops the newest event. |
| `packet-max-kib` | `256` | Packets larger than this go past plugin packet listeners untouched (1 to 2048). |
| `packet-timeout-ms` | `25` | How long a packet listener may wait for the plugin thread, and how long it may run (1 to 1000). |
| `[plugins.allow]` | none | Per plugin id, what the operator allows beyond the sandbox. |

```toml
[plugins]
enabled = true
queue-size = 256

[plugins.allow]
greeter = ["commands"]
lobby = ["network", "commands"]
```

The names in `[plugins.allow]` are `commands`, `network` and `packets`; any other name makes the file invalid and the
proxy refuses to start. See [plugin.toml](/docs/proxy/wasm-plugin-toml#capabilities) for what each one means.
The `[plugins]` table is read at startup: changing it needs a restart, and a `reload` that finds it changed is refused
as a whole. With `watch-files = true` under `[reload]` the proxy also reloads by itself when a file in the plugins
folder changes. See [Configuration](/docs/proxy/configuration) for the rest of `proxy.toml`.

## How a proxy plugin differs from a server plugin

A proxy plugin is written the same way as a server plugin, and the calls for events, commands, tasks, text, config and
player data are the same ones. These are the differences you will notice:

| | Proxy | Server |
|---|---|---|
| Threads | One plugin thread runs every callback of every plugin, one at a time | A callback runs on the part of the server that owns what it touches |
| Callback budget | 50 ms (2 s for the start of the plugin); five failures in a row switch the plugin off | About a quarter of a second; three failures in a row |
| Time | Tasks count steps of 50 ms | Tasks count ticks, 20 per second |
| Player handle | A player connected to the proxy, valid until they leave the proxy, not when they change backend | A player on that server |
| Import modules | Two (`basalt` and `basalt_proxy`), which the SDK hides from you | One |

Only a proxy plugin can work with backends, move players between them, change or refuse a login, a chat line, a command
or the server list entry, show boss bars and the tab list, open dialogs, offer resource packs, and listen to plugin
messages and relayed packets. Menus, placeholders, particles, sounds, worlds, entities, items and recipes belong to the
server and are not available on the proxy.
