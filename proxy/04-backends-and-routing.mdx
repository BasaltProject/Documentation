`config/servers.toml` defines where players go after they reach the proxy. `proxy.toml` defines how they reach it. Routes, groups and server definitions can be reloaded; health-check and status-relay timing settings require a restart.

## A complete two-server example

```toml
[routing]
try = ["lobby", "survival"]

[forced-hosts]
"survival.example.org" = ["survival", "lobby"]

[servers.lobby]
host = "127.0.0.1"
port = 25566
protocol = "auto"
forwarding = "basalt"

[servers.survival]
host = "10.0.0.12"
port = 25565
protocol = "auto"
forwarding = "velocity"
secret = "replace-with-the-backend-secret"
```

This example expects a Basalt lobby and a Velocity-forwarding backend. Configure their [forwarding](/docs/proxy/forwarding) to match before joining. DNS for `survival.example.org` must point at the proxy, not the survival backend.

## Server definitions

Use `[servers.<name>]`, with 1 to 256 servers per file. Names contain 1 to 64 ASCII letters, digits, `_` or `-`; use the same name in routes, commands and plugins.

| Key | Default | Meaning |
|---|---|---|
| `host` | `"127.0.0.1"` | Hostname, literal IPv4 or IPv6 address, without a port. DNS is resolved when connecting. |
| `port` | `25566` | Backend port, 1 to 65535. |
| `protocol` | `777` | Fixed Java protocol number, `"client"` or `"auto"`. |
| `forwarding` | required | `none`, `basalt`, `velocity`, `bungeecord`, `bungeeguard` or `safenet`. |
| `secret` | `""` | Required for Velocity, BungeeGuard and SafeNet, 1 to 4096 bytes without NUL. Leave empty or omit for other schemes. |
| `property-name` | `"safe_net_passphrase"` | SafeNet credential property. Only accepted for `safenet`. |
| `bungee-messages` | `false` | Allow this backend to use the BungeeCord messaging channel. |

A missing forwarding choice fails validation rather than selecting a weak scheme silently. `modern` aliases Velocity; `legacy` and `bungee` alias BungeeCord; `false` and `disabled` alias none. Prefer the canonical names above.

### Choosing a protocol

- A number describes the backend's actual Java protocol. For example, `777` is 26.3, `776` is 26.2 and `770` is 1.21.5.
- `"client"` means the backend accepts the player's protocol. Use it for a backend that performs its own translation.
- `"auto"` follows the client for Basalt forwarding and selects the current native protocol for other schemes. It is not network discovery of a Paper server's version.

Set a fixed number when the backend runs another version. The [version matrix](/docs/proxy/bedrock-and-versions#java-versions) explains the accepted pairs and the role of the Basalt session envelope.

## Default route and forced hosts

`[routing] try` is the default ordered route. `[forced-hosts]` maps the hostname in the player's handshake to another route. Comparison ignores case and one trailing dot; duplicate normalised names are refused. Hosts have no port, and the file may contain up to 256 forced-host entries.

```toml
[routing]
try = ["lobby"]

[forced-hosts]
"creative.example.org" = ["creative", "lobby"]
"play.example.org" = ["lobby"]
```

Define every named destination under `[servers]`, or as a server group. An unknown destination fails validation. Forced hosts choose an initial destination; they are not access-control rules for the game mode.

## Server groups

A group is an ordered collection of servers that can appear wherever a route takes a destination:

```toml
[server-groups.lobbies]
servers = ["lobby-1", "lobby-2"]

[routing]
try = ["lobbies", "survival"]
```

Groups contain server names, not other groups. Group names follow the server-name rules, cannot collide with a server and are limited to 256 groups. Expansion preserves order and removes repeated destinations. This is fallback, not load balancing: the first eligible available server wins, with no weights or least-player selection.

## Fallback and recovery

At login the proxy tries the route in order, skipping incompatible client/backend pairs and moving on after failed connection attempts. Each attempt is bounded by `connect-timeout-ms` and the overall login deadline. If no destination works, the player sees `No server is available right now. Please try again shortly.`

If an active backend unexpectedly drops during play, the proxy can recover to another backend of the player's route without a new public login. Visited destinations prevent automatic loops. If recovery exhausts the route, the player is disconnected. A successful explicit server change resets the recovery history.

Bedrock uses the first server of the default route and does not select a route from forced hosts. Do not assume Java's route fallback and switching behaviour applies to the Bedrock bridge.

## Health checks

```toml
[health]
enabled = true
mode = "status"
interval-seconds = 10
timeout-ms = 1500
failures-before-down = 2
```

| Key | Default | Meaning |
|---|---|---|
| `enabled` | `false` | Probe servers in the background. Off means servers are tried without advance checks. |
| `mode` | `"tcp"` | `tcp` checks the connection; `status` also requests Minecraft multiplayer-list status. |
| `interval-seconds` | `10` | Time between checks of a server, 1 to 3600 seconds. |
| `timeout-ms` | `1500` | Check timeout, 50 to 60000 ms. |
| `failures-before-down` | `2` | Consecutive failures before marking down, 1 to 100. One success brings it back. |

Routing prefers servers not marked down. If every candidate is down, it tries them anyway, so a bad check does not permanently lock players out. `/glist` and the [remote API](/docs/proxy/remote-api) expose server health. Changing this table requires a restart.

## Backend status relay

A profile in [`server_list.toml`](/docs/proxy/interface#backend-status-relay) can use `source = "server:lobby"` or `source = "route"` and selectively relay online count, slots, sample, MOTD, version or icon.

```toml
[status-relay]
ttl-ms = 5000
timeout-ms = 1500
```

`ttl-ms` is the cache lifetime (100 to 3600000 ms); `timeout-ms` bounds a query (50 to 60000 ms). While a result is pending or unavailable, the profile uses its local values. These timings require a restart and are independent of health checks.

## Moving players

Players with `basalt.command.server` can use `/server` and `/server <name>`. Staff with `basalt.command.send` can run `/send <player> <server>` or `/send all <server>`. A plugin can use the [player API](/docs/proxy/wasm-players#moving-a-player).

A move is refused if the target does not exist, the player is not in play, the destination is current, another move is pending or the protocol pair is incompatible. Accepted preparation is not a guarantee that the destination will finish login. From 1.20.2, Java clients reconfigure in place; older clients receive a new join sequence.

See [Commands](/docs/proxy/commands) for names, permissions, aliases and backend command collisions.

## BungeeCord messages

Enable `bungee-messages = true` only on a backend you want to control the proxy. It can then use `bungeecord:main` or legacy `BungeeCord`:

| Subcommand | Effect |
|---|---|
| `Connect` | Request a move of the sending player to another backend. |
| `GetServer`, `GetServers` | Query current server or configured server names. |
| `UUID` | Query the player's UUID. |
| `PlayerCount`, `PlayerList` | Query players on a named server or `ALL`. |
| `IP`, `ServerIP` | Query player or backend address information. |
| `Forward` | Forward a plugin message between backends. |

`PlayerCount`, `PlayerList`, `IP`, `ServerIP` and `Forward` also need the plugin host enabled. Messages received from a player's client are discarded. This messaging support does not load BungeeCord Java plugins and does not require the backend to use BungeeCord forwarding.

## Applying changes

Run `reload` after changing server definitions, groups or routes. Existing sessions keep their routing snapshot; new sessions use the new topology. A missing server name, invalid secret or malformed file is reported rather than silently replaced by defaults.
